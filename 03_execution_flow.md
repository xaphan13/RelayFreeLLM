# 03. Логика и работа кода (Execution Flow)

## Жизненный цикл приложения

Жизненный цикл управляется механизмом `lifespan` в FastAPI (`src/server.py`):

1. **Инициализация (Startup):**
   - Настройка глобального логгера (`ProjectLogger`).
   - Инициализация `ProviderRegistry`: авто-обнаружение клиентов в `src/api_clients/` и валидация ключей доступа (наличие в окружении).
   - Инициализация `ModelSelector`: загрузка конфигурации моделей из `provider_model_limits.json`.
   - **Синхронизация:** Проверка пересечения доступных провайдеров (по ключам) и провайдеров в конфигурации JSON. Провайдеры без ключей или без конфигурации отключаются. Если доступных провайдеров нет, приложение завершает работу с ошибкой.
   - Инициализация сервисов хранения состояния: `ConversationStore` и `UsageTracker`.
   - Создание корневого `ModelDispatcher` и инъекция всех сервисов в глобальный контекст `app.state`.
2. **Запуск:** FastAPI запускает ASGI-сервер (`uvicorn`), приложение начинает принимать HTTP-запросы.
3. **Завершение работы (Shutdown):**
   - Корректное завершение обработки текущих запросов.
   - Логирование остановки. (Примечание: на данный момент нет явного механизма сброса in-memory состояния rate-limits на диск при graceful shutdown).

## Роутинг и Middleware

- **Middleware:** Используется только встроенный `CORSMiddleware` для разрешения кросс-доменных запросов ко всем эндпоинтам.
- **Роутинг:**
  - Основной API в `src/router.py` монтируется в корень.
  - Административный API в `src/admin.py` монтируется для `/admin` и содержит эндпоинты для управления лимитами и просмотра использования.
  - Эндпоинты получают сервисы (например, диспетчер) через зависимости `Depends(get_dispatcher)`.

## Ключевые бизнес-процессы (Step-by-step)

### Обработка запроса на генерацию текста (`/v1/chat/completions`)

1. Запрос поступает в `create_chat_completion` (`src/router.py`).
2. Извлекаются мета-данные: `model` (может быть как конкретной моделью, так и "meta-model"), параметры фильтрации (`model_type`, `model_scale`), наличие картинок, флаг `stream` и заголовок `X-Session-ID`.
3. Роутер вызывает асинхронный метод `dispatcher.dispatch(request, session_id, use_server_system_prompt)`.
4. **Выбор моделей (`selector.select_models`)**: Возвращает отсортированный приоритетный список кандидатов на основе фильтров, доступных лимитов и истории ошибок.
5. **Цикл Fallback'а (`dispatcher.dispatch`):**
   - Перебирает список кандидатов.
   - Выполняет учет rate limits (`limits_tracker.consume`).
   - Применяет контекстные стратегии и нормализацию.
   - Вызывает `provider_client.call_model_api`.
   - В случае успеха прерывает цикл и возвращает ответ (или генератор стрима).
   - В случае ошибки (`RateLimitError`, `ProviderUnavailableError`) логирует сбой, обновляет счетчик ошибок для модели, и переходит к следующей итерации.
6. **Возврат клиенту:** Если запрос потоковый (`stream=True`), возвращается `StreamingResponse`, читающий асинхронный генератор. Иначе возвращается JSON-ответ `ChatCompletionResponse`. Если все кандидаты исчерпаны, выбрасывается `AllProvidersExhaustedError` (503 Service Unavailable).

## Обработка ошибок и логирование

- **Исключения:** Иерархия ошибок определена в `src/exceptions.py` (базовый `ProviderError`, от него `RateLimitError`, `AuthenticationError`, и т.д.).
- **Глобальный обработчик:** FastAPI перехватывает `HTTPException` в роутере, но основная обработка логики "retry" происходит внутри диспетчера (try-except в цикле).
- **Логирование:** Используется кастомный `ProjectLogger` (`src/logging_util.py`). Логи пишутся как в `stdout` (консоль), так и в файлы с ротацией по времени и компрессией (`CompressedTimedRotatingFileHandler`). Это обеспечивает сохранность истории работы без переполнения диска.
