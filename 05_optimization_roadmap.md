# 05. Предложения по развитию (Optimization Roadmap)

## Архитектурные улучшения

1. **Персистентное состояние Rate-Limits и Кэширование:**
   - **Проблема:** In-memory rate limits сбрасываются при рестарте; отсутствие кэша запросов.
   - **Решение:** Внедрить опциональную поддержку **Redis**. Использовать Redis для хранения "корзин" токенов (Token Bucket) и счетчиков запросов. Это также позволит горизонтально масштабировать шлюз (запускать несколько экземпляров `uvicorn`/`gunicorn` воркеров), не боясь рассинхронизации лимитов. Внедрить семантическое кэширование одинаковых промптов для экономии бесплатных лимитов.

2. **Безопасная конкурентная запись (Concurrency Control):**
   - **Проблема:** Возможные race conditions при записи JSON-статистики и истории.
   - **Решение:** Перевести хранение истории и статистики на легковесную SQLite базу данных (с использованием асинхронного драйвера, например, `aiosqlite` или `SQLAlchemy` + `asyncpg`). SQLite лучше справляется с конкурентными транзакциями, чем ручная перезапись JSON-файлов.

3. **Propagating Cancellation (Отмена запросов):**
   - **Проблема:** Если клиент разрывает соединение во время стриминга, шлюз может продолжать качать данные от провайдера, тратя rate-limits и ресурсы.
   - **Решение:** Связать контекст запроса FastAPI (через `Request.is_disconnected()`) с токенами отмены (cancellation tokens) `httpx` клиента, чтобы прерывать HTTP-запрос к провайдеру при отключении клиента.

## Оптимизация производительности

1. **Снижение накладных расходов при стриминге:**
   - В циклах обработки чанков (чтение из `httpx` и `yield` в FastAPI) минимизировать выделение объектов (например, переиспользование Pydantic-моделей или прямой возврат сырых байт-строк там, где нормализация не требуется) для снижения нагрузки на Garbage Collector.

2. **Оптимизация TF-scoring (алгоритм "Reservoir"):**
   - Анализ текста и выделение значимых предложений для сжатия контекста может быть затратным на больших объемах (десятки тысяч токенов).
   - **Улучшение:** Использовать более быстрые C-оптимизированные библиотеки (например, спайсинг через `spacy` или переписать тяжелые участки на Cython/Rust-extensions).

## Рефакторинг (Первоочередные цели)

1. **`src/model_dispatcher.py`:**
   - Файл слишком велик (божественный класс `ModelDispatcher`).
   - **Действие:** Вынести логику `FallbackStrategy` и обработки ошибок в отдельный модуль. Оставить диспетчеру только высокоуровневую оркестрацию.
2. **`src/api_clients/` (Дублирование кода):**
   - Клиенты часто повторяют код обработки потоков (SSE).
   - **Действие:** Перенести логику парсинга SSE и обработки HTTP-статусов (401, 429, 500) в базовый `ApiInterface`, используя паттерн Template Method, оставив клиентам только подготовку payload'а и извлечение данных из конкретных форматов ответов.

## Улучшение Developer Experience (DX)

1. **Тестирование (CI/CD):**
   - Внедрить фреймворк `pytest`.
   - Написать mock-тесты (используя `respx` или `pytest-httpx`) для симуляции ответов провайдеров (в т.ч. ошибок 429) и проверки корректности переключений диспетчером.
   - Настроить GitHub Actions для автоматического запуска линтеров (`ruff` / `flake8`, `mypy`) и тестов при PR.

2. **Локальный запуск и Развертывание:**
   - Предоставить полнофункциональный `docker-compose.yml`, который разворачивает не только сам сервер, но и (опционально) экземпляр Redis и Ollama, чтобы показать production-ready настройку "из коробки".

3. **Документация кода:**
   - Добавить автоматическую генерацию API-документации (помимо встроенного Swagger UI), возможно, с использованием `MkDocs` для описания архитектуры и процесса добавления новых провайдеров.
