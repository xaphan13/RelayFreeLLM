# 02. Архитектура и паттерны (Architecture)

## Высокоуровневая архитектура
Проект представляет собой **монолитный API-шлюз (Gateway)** с асинхронной неблокирующей архитектурой на базе FastAPI. Шлюз действует как прокси-маршрутизатор (reverse proxy с логикой): он принимает запросы в формате OpenAI API, выполняет сложную логику выбора провайдера (роутинг), применяет rate-limiting, отправляет запросы к целевому провайдеру (через `httpx`), обрабатывает ошибки и возвращает унифицированный результат клиенту (включая стриминг).

## Основные паттерны проектирования

1. **Dependency Injection (DI) и Inversion of Control (IoC):**
   - Экземпляры основных сервисов (`ProviderRegistry`, `ModelSelector`, `ModelDispatcher`, `UsageTracker`, `ConversationStore`) создаются один раз при старте (`src/server.py`) и внедряются в `app.state`.
   - В роутах (`src/router.py`) используются функции-зависимости (Depends) для получения этих сервисов, что облегчает тестирование и делает код слабосвязанным.

2. **Registry / Авто-обнаружение (Auto-Discovery):**
   - `ProviderRegistry` (`src/provider_registry.py`) использует интроспекцию модулей в `src/api_clients/` для динамического поиска классов, унаследованных от `ApiInterface`. Это позволяет добавлять новых провайдеров созданием одного файла-класса без изменения центрального реестра.

3. **Strategy (Стратегия):**
   - Реализован через абстрактный базовый класс `ApiInterface` (`src/api_clients/api_interface.py`). Диспетчер работает с абстрактным интерфейсом, а конкретная реализация вызова API делегируется классам-потомкам (например, `GroqClient`, `GeminiClient`).
   - `ContextManager` (`src/context_manager.py`) использует паттерн Стратегия для различных режимов обработки контекста (`static`, `dynamic`, `reservoir`, `adaptive`).

4. **Circuit Breaker / Retry (Предохранитель и Повторные попытки):**
   - Логика в `ModelDispatcher` (`src/model_dispatcher.py`) перехватывает ошибки от провайдеров (`RateLimitError`, `ProviderError`). При сбое (или ограничении по rate limit) диспетчер прозрачно ищет следующего подходящего провайдера и повторяет запрос без возврата ошибки клиенту.

5. **Token Bucket / Leaky Bucket:**
   - Паттерны для ограничения скорости (rate limiting), реализованные в `ApiLimitsTracker` (`src/api_limits_tracker.py`), контролируют использование ресурсов провайдеров на уровне запросов и токенов (секунды, минуты, часы, дни).

## Схема потока данных (Data Flow)

1. **Точка входа (Entry Point):** Клиент отправляет POST-запрос на `/v1/chat/completions` (OpenAI-compatible) в `src/router.py`.
2. **Пре-процессинг:** Запрос парсится в модель `ChatCompletionRequest` (Pydantic). Проверяются заголовки (например, `X-Session-ID`, `X-Use-ServerSide-System-Prompt`).
3. **Управление контекстом:** `ContextManager` (вызывается из `ModelDispatcher`) анализирует `messages`, обрезает или суммаризирует контекст в зависимости от выбранного режима.
4. **Нормализация запроса:** В системный промпт (если не отключено) инжектируется `style_config` для унификации ответов.
5. **Выбор модели (Routing):** `ModelSelector` (`src/model_selector.py`) на основе параметров `model` (например, "meta-model" или фильтров "coding", "large") и наличия мультимодальности (картинок) возвращает список подходящих моделей, отсортированных по доступности и rate limits (отслеживается `ApiLimitsTracker`).
6. **Диспетчеризация и Вызов:** `ModelDispatcher` (`src/model_dispatcher.py`) берет первую модель из списка. Из `ProviderRegistry` извлекается соответствующий клиент (например, `MistralClient`). Вызывается `call_model_api`.
7. **Failover (Авто-замена):** Если клиент возвращает ошибку (например, 429 Rate Limit), диспетчер логирует ее, помечает провайдера временно недоступным (через `ApiLimitsTracker`), и переходит к следующей модели в списке (возврат на шаг 6).
8. **Пост-процессинг:** Полученный ответ (строка или стрим) прогоняется через `ResponseNormalizer` (`src/response_normalizer.py`) для удаления специфичных артефактов (например, "As an AI..."). Обновляется `UsageTracker`.
9. **Возврат ответа:** Нормализованный ответ упаковывается в формат `ChatCompletionResponse` (или Server-Sent Events стрим) и отправляется клиенту.

## Управление состоянием, кэшированием и конфигурациями

- **Конфигурация (Configuration):** Управляется классом `Settings` (Pydantic) в `src/config.py`. Переменные загружаются из окружения (файл `.env`).
- **Модели и Лимиты:** Хранятся в JSON-файле `src/provider_model_limits.json`. Изменения через админку обновляют файл и "на лету" обновляют состояние в памяти (`ModelSelector`).
- **Состояние лимитов (Rate Limits):** Хранится in-memory в экземпляре `ApiLimitsTracker`. При рестарте сервера сбрасывается.
- **Статистика использования:** `UsageTracker` накапливает статистику in-memory и периодически сбрасывает ее в файл `usage_stats.json` (примитивное персистентное хранилище).
- **История чатов:** `ConversationStore` опционально сохраняет историю чатов (для веб-интерфейса) в `conversations.json`.
- **Session Affinity (Привязка сессии):** `ModelDispatcher` хранит in-memory словарь `_session_affinity`, привязывая `session_id` к конкретному провайдеру/модели для оптимизации кэширования контекста на стороне провайдера.
